Codex를 쓰다 보니 평소 머릿속에만 있던 아이디어가 생각보다 빨리 화면으로 나왔다. 처음에는 재미로 만들었지만, 막상 내가 계속 쓰고 싶은 서비스가 생기자 다른 문제가 나타났다. **이걸 어디에 두고, 어떻게 계속 살아 있게 할까?**

그중 하나가 이력서 원문을 보존하면서 수정할 위치와 근거를 제안하는 `resume-agent`였다. 개인적으로 쓰던 도구를 실제 웹 서비스로 옮겨보고 싶었지만, 작은 서비스가 하나 늘 때마다 서버 임대료까지 늘리는 건 부담스러웠다. 집에는 이미 원격 접속을 위해 켜두는 맥미니가 있었다. 그래서 “간단한 서비스라면 이 컴퓨터로 운영해도 되지 않을까?”라는 생각으로 시작했다.

## 서버를 새로 빌리지 않고, 이미 가진 컴퓨터를 쓰기

맥미니는 M4, 메모리 16GB, 내장 저장소 256GB인 기본 모델이다. 저장 공간이 아쉬워 2TB 외장 SSD를 연결해 쓰고 있었다. 이 사양으로 여러 사람이 동시에 쓰는 서비스를 감당할 수 있는지는 알 수 없었다. 다만 초대받은 소수만 사용하는 서비스의 API와 문서 처리를 시험해보기에는 출발점이 될 수 있겠다고 생각했다.

처음에는 AI를 쓰는 서비스라 서버 성능도 꽤 높아야 할 거라 막연히 생각했다. 실제 구성을 나눠보니 맥미니가 맡는 일은 문서 추출·OCR, 파일 저장, API 응답이고, AI 추론 자체는 OpenAI API에서 실행된다. 컴퓨터 사양보다 먼저 고민해야 할 것은 **외부에서 안전하게 들어오는 길과 데이터를 남기는 방법**이었다.

전기료가 완전히 공짜가 되는 것도 아니다. 원래 켜두던 컴퓨터를 활용한다는 판단이었을 뿐, 이 서비스를 돌린 뒤 소비 전력을 따로 측정하지는 않았다. 임대료를 줄이는 대신 내가 직접 운영할 시간을 쓰는 선택에 더 가깝다.

## 화면은 바깥에, 데이터는 집에

집 공유기에서 포트를 열고 맥미니의 주소로 요청을 보내는 방법도 있다. 하지만 개인 서비스를 위해 집 네트워크에 공개 진입점을 만드는 것보다, 이미 접속과 인증을 다루는 서비스를 이용하는 편이 낫겠다고 판단했다. 최종적으로는 Cloudflare가 접속을 받고, 맥미니는 필요한 API만 처리하도록 나눴다.

사용자가 사이트를 열면 Cloudflare Access가 로그인을 확인하고, Worker가 화면 파일을 전달한다. 브라우저에서 화면이 실행되므로 첫 화면을 보여주기 위해 맥미니가 HTML을 매번 만들 필요는 없다. 이력서를 저장하거나 검토할 때만 `/api/*` 요청이 집으로 들어온다.

그 요청은 Worker의 VPC Service에서 Tunnel을 거쳐 맥미니의 FastAPI로 전달된다. 맥미니에서는 `cloudflared`가 먼저 Cloudflare 쪽으로 연결을 유지하고, API 서버는 같은 컴퓨터의 `127.0.0.1:8000`에서만 요청을 받는다. 공유기의 인바운드 포트를 열거나 고정 공인 IP를 준비할 필요가 없는 이유다. [Cloudflare Tunnel](https://developers.cloudflare.com/workers-vpc/configuration/tunnel/)과 [VPC Service](https://developers.cloudflare.com/workers-vpc/configuration/vpc-services/)가 각각 연결과 목적지 지정을 맡는다.

그렇다고 Tunnel만 있으면 인증이 끝나는 것은 아니다. Access가 입구에서 사용자를 확인하고, FastAPI도 전달받은 토큰과 계정 상태를 검증한 뒤 해당 사용자의 자료만 읽도록 했다. 관리용 SSH에 쓰는 Tailscale과 웹 사용자가 들어오는 경로도 별개다.

## 외장 SSD에 저장하고, 다른 디스크에 백업하기

이력서 원본과 첨부 파일, 작업 데이터는 맥미니에 연결한 외장 SSD에 둔다. SQLite에는 파일의 위치와 소유자 같은 정보를 기록하고, 파일 본문은 디스크에 저장한다. AI 검토에 필요한 내용은 서버에서 OpenAI API로 보내므로 “집에서 운영한다”가 모든 데이터가 집 밖으로 나가지 않는다는 뜻은 아니다.

여기서 외장 SSD만 믿을 수는 없었다. 디스크 하나가 고장 나면 원본과 DB를 함께 잃을 수 있기 때문이다. 그래서 예약 백업과 서버 교체 전 백업을 만들고, 암호화한 사본을 **맥미니 내장 디스크**에 보관하도록 했다. 백업을 같은 외장 SSD에 두는 것보다는 낫지만, 맥미니 자체를 잃으면 두 디스크를 함께 잃을 수 있다. 아직 장치 밖 복구 사본까지 마련한 구조는 아니다.

백업 파일이 있다는 사실만으로 복구가 보장되지는 않는다. 운영 기록에서는 DB를 별도 위치에 복원해 무결성을 확인했고 가상 첨부 파일의 복원도 시험했다. 실제 사용자가 올린 모든 자료와 암호화 키까지 포함해 재난 상황에서 끝까지 되살리는 과정은 여전히 확인이 필요하다.

## 코드를 실행하는 것과 운영하는 것은 달랐다

실제로 마주친 문제는 성능보다 운영 환경에 있었다. 터미널에서 성공한 백업이 macOS의 `launchd`에서 실행될 때는 외장 볼륨 접근 권한 때문에 실패했다. 실행 주체를 정리하고 해당 앱에 제거 가능한 볼륨 접근을 허용한 뒤 다시 확인했다. 서버를 교체할 때는 실행기가 자식 Python 프로세스를 남겨 종료와 재시작이 어긋나는 문제도 있었다. `launchd`가 관리하는 프로세스와 실제 API 프로세스가 일치하도록 실행 방식을 고쳤다.

배포도 단순히 GitHub에서 집 컴퓨터로 SSH 접속하는 방식은 쓰지 않았다. 프런트엔드는 GitHub의 검사 후 Cloudflare에 배포하고, 백엔드는 맥미니가 배포 요청과 검사 결과를 조회해 검증된 코드를 가져온다. 서버를 멈추고 백업한 뒤 새 코드를 시작해 상태를 확인한다. 백업이 실패하면 새 버전으로 바꾸지 않는다. 이 과정에서 Cloudflare 쪽 배포 토큰에는 VPC Service를 연결할 권한도 필요하다는 것을 실제 배포 오류를 통해 알게 됐다.

Codex 덕분에 기능을 만드는 속도는 빨라졌지만, 컴퓨터가 꺼졌을 때 화면과 API가 각각 어떻게 보이는지, 백업이 실제로 복원되는지, 배포 중인 요청은 어떻게 되는지까지 대신 책임져주지는 않는다. 코드를 만드는 일이 끝나자 오히려 “내가 이 서비스를 계속 돌볼 수 있나?”라는 질문이 시작됐다.

## 아직은 작은 서비스에 맞는 답

2026년 9월 말 기준으로 로그인, API 연결, 서버 상태 확인, 프런트·백엔드 배포와 백업·재시작은 확인했다. 반면 실제 사용자 시나리오 전체에서 AI 검토와 OCR이 안정적으로 이어지는지, 맥미니 전체를 재부팅한 뒤 로그인·외장 SSD 연결까지 자동으로 회복되는지는 별도 검증이 남아 있었다. 현재 구성도 사용자 로그인 이후 실행되는 `launchd`에 의존한다.

집 인터넷이나 전원이 끊기면 Cloudflare에 올라간 화면은 열려도 집의 API는 쓸 수 없다. 사용자가 늘거나 상시 가용성이 중요해지면 지금의 구조를 다시 판단해야 한다. 그럼에도 내가 계속 써보고 싶은 작은 서비스를 위해서는 꽤 의미 있는 출발이었다. 서버 요금을 아끼는 방법을 찾다가, 결국 **서비스를 운영한다는 것이 무엇인지** 조금 더 구체적으로 배우게 됐다.

구체적인 구성과 당시 검증 범위는 [resume-agent의 운영 기록](https://github.com/Yelihi/resume-agent#아키텍처-이해하기)에 남겨두었다.
